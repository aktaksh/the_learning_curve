01 · FOUNDATIONS

Where do system calls fit in Linux?

A Linux program normally runs in user space, with limited privileges. The kernel manages hardware, process scheduling, virtual memory, files, and networking. A system call is a controlled entry point that lets a program request kernel services.

USER SPACE Shell · Text editor · Your C program · libc
↓ request (read(), fork())   ↑ result / error
SYSTEM CALL INTERFACE Controlled transition into kernel mode
↓ kernel services ↑
KERNEL SPACE Scheduler · VFS · Memory management · Device drivers
↓
HARDWARE CPU · RAM · SSD · Network interface

System call vs. ordinary C function

strlen("linux")

Runs as a normal library function in user space. It does not itself need to enter the kernel.

write(1, "Hi", 2)

The libc wrapper requests the Linux write system call to write bytes to a file descriptor.

Terminology: printf() is a C standard-library function, not itself a Linux system call. It usually buffers output and ultimately uses a write operation to send it to a file/terminal. fork() is the familiar POSIX interface; on modern Linux its libc implementation typically uses the clone system call.
02 · CORE CONCEPT

What exactly is a system call?

A system call is the mechanism by which a user-space program asks the Linux kernel to perform a protected operation. The CPU changes execution privilege while servicing the request, then returns control to the application.

1Your C code calls write().
2The C library wrapper prepares arguments and invokes the kernel entry mechanism.
3The kernel validates the request and accesses a file/terminal.
4The wrapper returns bytes written or -1, setting errno on error.

First system-call program: write to standard output

01 · hello_write.c · C
#include <unistd.h>
#include <stdio.h>

int main(void) {
    const char msg[] = "Hello from write()!\n";
    ssize_t count = write(STDOUT_FILENO, msg, sizeof(msg) - 1);
    if (count == -1) {
        perror("write failed");
        return 1;
    }
    return 0;
}

System calls are grouped by the job they perform. This classification helps students know which kernel service a program is requesting.

Detailed reference: what each family does

Learn the purpose, inputs, result and failure modes of each operation. The names below mix Linux kernel syscalls with familiar C/POSIX wrappers. Use man 2 NAME for syscall interfaces, and man 3 NAME for library routines.

01 · Process creation & execution

Common APIs: fork(), clone(), execve(), wait4(), exit(), getpid(), getppid(), kill()

Use case: Start another process; identify it; wait for its result; send a signal.

Understand: fork returns 0 in child, child PID in parent; execve replaces the current process image; wait collects termination status.

02 · Files & directories

Common APIs: open()/openat(), read(), write(), close(), lseek(), stat()/newfstatat(), mkdir(), unlink(), rename()

Use case: Open a settings file, stream its bytes, create folders and rename files.

Understand: File descriptors are per-process integers; read may return fewer bytes; write may partially complete; close releases a descriptor.

03 · Virtual memory

Common APIs: mmap(), munmap(), mprotect(), brk(), madvise()

Use case: Map a shared library, allocate memory, create a file-backed mapping.

Understand: mmap creates a virtual memory mapping; mprotect changes permissions; malloc is a library allocator, not itself a syscall.

04 · Devices & terminal I/O

Common APIs: ioctl(), read(), write(), poll(), epoll_wait()

Use case: Read from a terminal/serial port or wait for a device to become ready.

Understand: Many devices are exposed through files such as /dev/tty; ioctl is device-specific; polling waits for readiness.

05 · Interprocess communication

Common APIs: pipe()/pipe2(), shmget(), shmat(), msgget(), msgsnd(), msgrcv(), futex()

Use case: Pipe a producer into a consumer or synchronize worker threads.

Understand: Pipes transfer bytes; shared memory shares pages; futex helps userspace synchronization; not every interface here is POSIX.

06 · Networking

Common APIs: socket(), bind(), listen(), accept(), connect(), sendto(), recvfrom(), shutdown()

Use case: Implement a TCP web server or connect to another machine.

Understand: Sockets also use descriptors; socket creates an endpoint; bind selects a local address; accept accepts a connection.

07 · Identity, permissions & metadata

Common APIs: getuid(), geteuid(), setuid(), chmod(), chown(), umask(), uname(), clock_gettime()

Use case: Check permissions, change file mode, read system information.

Understand: Real/effective IDs matter for permissions; chmod changes mode bits; many APIs have libc wrappers.

08 · Signals, timers & scheduling

Common APIs: rt_sigaction(), rt_sigprocmask(), nanosleep(), sched_yield(), setpriority()

Use case: Handle shutdown signals, pause for a timer, change scheduling priority.

Understand: Signals report asynchronous events; handlers have severe restrictions; nanosleep may be interrupted.

Important distinction: printf(), malloc(), getenv() and exit() are C library functions, not direct Linux system calls. In contrast, read() and write() are POSIX functions wrapping kernel services. execvp() searches PATH in the library and eventually invokes execve().
04 · HANDS-ON

Read and write a file using system-call interfaces

Readability guide: light explanation panels with dark-on-light text; terminal and syntax-highlighted code retain dark backgrounds with high-contrast light code. Use the horizontal scrollbar for long commands on smaller screens.

Real-life use case: a server reads configuration from disk. A file is represented to a process by a small integer called a file descriptor. Common defaults are 0 (stdin), 1 (stdout), and 2 (stderr).

0STDIN
1STDOUT
2STDERR
3+Opened files / sockets / pipes

How the file-descriptor model works

C programopen("notes.txt", O_RDONLY)
libc wrapperInvokes kernel interface
Kernel descriptor tablefd = 3 → open file description
Filesysteminode / page cache / storage

A file descriptor is an integer index in a process-owned table. The kernel's open file description stores access mode and current offset. Two duplicated descriptors can share one file offset, and descriptors inherited across fork() refer to the same open file description.

Function-by-function reference

FunctionPurpose and argumentsReturn value / common errors
open(path, flags, mode)Open a pathname; mode applies when creating a file. Flags include O_RDONLY, O_WRONLY, O_RDWR, O_CREAT, O_TRUNC, O_APPEND.Nonnegative fd, or −1 with errno such as ENOENT/EACCES. Effective permissions are affected by umask.
read(fd, buf, count)Transfer up to count bytes from descriptor to memory at buf. It does not append a C string terminator.ssize_t bytes (possibly fewer), 0 at EOF, or −1 on error; EINTR/EAGAIN are possible.
write(fd, buf, count)Transfer up to count bytes from memory to descriptor. A partial write is possible.ssize_t bytes written, or −1. Retry remaining bytes where appropriate.
close(fd)Release a descriptor; never use it after successful close. Closing does not necessarily mean data reached physical storage.0 or −1. Linux advises against blindly retrying close after EINTR due to descriptor reuse hazards.
lseek(fd, offset, whence)Change file offset with SEEK_SET, SEEK_CUR or SEEK_END. Pipes and sockets are not seekable.New offset or −1, often ESPIPE for a pipe.
fsync(fd)Request synchronized transfer of modified file data and metadata to storage.0 or −1; use when durability matters, with filesystem/hardware caveats.
Example: open("report.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644) asks for write-only access, creates if missing, clears prior content, and requests rw-r--r-- before umask. Prefer O_CLOEXEC in applications where descriptors should not leak across an exec().
03 · file_io.c · C
#include <fcntl.h>
#include <stdio.h>
#include <unistd.h>

int main(void) {
    const char data[] = "Linux system calls\n";
    char buf[64];
    int fd = open("demo.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (fd == -1) { perror("open for writing"); return 1; }
    if (write(fd, data, sizeof(data) - 1) != sizeof(data) - 1) {
        perror("write"); close(fd); return 1;
    }
    if (close(fd) == -1) { perror("close"); return 1; }

    fd = open("demo.txt", O_RDONLY);
    if (fd == -1) { perror("open for reading"); return 1; }
    ssize_t n = read(fd, buf, sizeof(buf));
    if (n == -1) { perror("read"); close(fd); return 1; }
    if (write(STDOUT_FILENO, buf, (size_t)n) != n) {
        perror("stdout write"); close(fd); return 1;
    }
    if (close(fd) == -1) { perror("close"); return 1; }
    return 0;
}

What students should observe

open() returns a descriptor; write() transfers bytes; close() releases the descriptor; and read() returns the number of bytes read, zero at end-of-file, or -1 on error.

Production-minded example: read until EOF and handle short writes

This program behaves like a small cat: it reads chunks instead of assuming one read() will return the whole file. It also handles interruptions while copying bytes.

🔴 🟡 🟢  robust_read.c · C
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <unistd.h>

int main(void) {
    char buf[4096];
    int fd = open("demo.txt", O_RDONLY);
    if (fd < 0) { perror("open"); return 1; }
    for (;;) {
        ssize_t n = read(fd, buf, sizeof buf);
        if (n == 0) break;                 // End of file
        if (n < 0) {
            if (errno == EINTR) continue;  // Interrupted: retry
            perror("read"); close(fd); return 1;
        }
        ssize_t offset = 0;
        while (offset < n) {
            ssize_t w = write(STDOUT_FILENO, buf + offset,
                              (size_t)(n - offset));
            if (w < 0 && errno == EINTR) continue;
            if (w <= 0) { perror("write"); close(fd); return 1; }
            offset += w;                    // Handle partial writes
        }
    }
    if (close(fd) < 0) { perror("close"); return 1; }
    return 0;
}

05 · PROCESS MODEL

A program on disk is not a running process

A program is executable code stored on disk. A process is a running instance with its own virtual address space, execution state, open descriptors, credentials, environment, and kernel bookkeeping.

Program

Executable file: /usr/bin/sleep. Passive bytes on storage.

Process

Running sleep 60. It has a PID, memory mappings, open file descriptors, and a scheduler state.

🆔

PID / PPID

Linux assigns a process ID; PPID identifies its current parent.

🧠

Address space

Each process normally sees its own virtual memory.

📂

Open descriptors

Files, sockets and pipes are referenced through descriptors.

⏱️

Scheduling state

The kernel tracks whether a task is runnable, sleeping or stopped.

06 · C FUNDAMENTALS

Command-line arguments and environment

Arguments are how the shell passes input to a new program. With int main(int argc, char *argv[]), argc counts arguments including the program name, and argv holds pointers to null-terminated strings. argv[argc] is a null pointer.

$ ./greet Alice 3

05 · greet.c · C
#include <stdio.h>
#include <stdlib.h>

int main(int argc, char *argv[]) {
    if (argc != 3) {
        fprintf(stderr, "Usage: %s NAME TIMES\n", argv[0]);
        return 1;
    }
    char *end;
    long times = strtol(argv[2], &end, 10);
    if (*end != '\0' || times < 1 || times > 5) {
        fprintf(stderr, "TIMES must be 1..5\n");
        return 1;
    }
    for (long i = 0; i < times; i++)
        printf("Hello, %s!\n", argv[1]);
    return 0;
}

07 · VISUAL EXPLANATION

Inside a process: text, data, BSS, heap and stack

Linux gives each process a virtual address space. A common simplified layout looks like this; actual addresses and ordering depend on architecture, ASLR, mappings, and the loader. The diagram is conceptual, not an ABI promise.

Higher virtual addresses ↑
STACKFunction frames, parameters, local variables · often grows downward ↓

MMAP / SHARED LIBRARIESMapped files, shared libraries, anonymous mappings

Walk through an example address space

The process sees a virtual address space mapped to physical memory by the kernel and CPU memory-management unit. The segments below describe logical roles, not fixed physical addresses. On a typical 64-bit Linux ELF executable, regions may be separated by large unmapped gaps and reordered by ASLR.

Stack ↓Function call frames, local automatic variables, return information; thread stacks are separate
Mapped regionsShared libraries (.so), mapped files, anonymous mappings and often large malloc allocations
Heap ↑ (conceptual)Dynamic storage owned by allocator: malloc/calloc/realloc/free; allocation is not always contiguous
.bssZero-initialized or uninitialized globals and static variables; does not need matching bytes stored in ELF
.dataInitialized writable global/static objects, e.g. int counter = 10
.text + .rodataMachine instructions and read-only constants / string literals (often separate memory protections)

Global vs local

int global = 5; normally lives in initialized data. int count; at file scope normally lives in BSS. int local = 5; inside a function usually has automatic storage, conceptually in its stack frame, though optimized registers are possible.

Static keyword

static int x = 7; inside a function is not recreated on every call: it has static storage duration and normally lives in DATA. static int x; normally lives in BSS.

Heap ownership

malloc(100) allocates storage and returns a pointer. free(p) releases the allocation to the allocator; it does not always immediately return physical pages to the kernel.

Stack overflow

Very deep recursion or huge automatic arrays can exhaust stack limits. Inspect ulimit -s; prefer bounded recursion and appropriately sized allocations.

06 · memory_demo.c · C
#include <stdio.h>
#include <stdlib.h>

int global_init = 42;           // data
int global_zero;                // BSS
static int static_value = 7;    // data

int main(void) {
    int local = 100;            // stack
    int *dynamic = malloc(sizeof(*dynamic));  // heap
    if (dynamic == NULL) return 1;
    *dynamic = 200;

    printf("main (text)    : %p\n", (void *)main);
    printf("global (data)  : %p\n", (void *)&global_init);
    printf("static (data)  : %p\n", (void *)&static_value);
    printf("global (BSS)   : %p\n", (void *)&global_zero);
    printf("heap           : %p\n", (void *)dynamic);
    printf("stack          : %p\n", (void *)&local);
    free(dynamic);
    return 0;
}

💡 Address values depend on machine, run, architecture and ASLR. Printing a function pointer via %p is not strictly portable ISO C, but is widely used on Linux systems; for rigorous portable examples, avoid assuming function and object pointers are identical.

07 · fork_basic.c · C
#include <stdio.h>
#include <unistd.h>
#include <sys/types.h>

int main(void) {
    pid_t pid = fork();
    if (pid < 0) {
        perror("fork");
        return 1;
    } else if (pid == 0) {
        printf("CHILD: pid=%ld, ppid=%ld\n",
               (long)getpid(), (long)getppid());
    } else {
        printf("PARENT: pid=%ld, child=%ld\n",
               (long)getpid(), (long)pid);
    }
    return 0;
}

What gets copied? What gets shared?

The child gets its own virtual address space, but Linux implements this efficiently with copy-on-write (COW). Initially, many physical pages are shared read-only; pages are copied when modified. Open file descriptors refer to the same underlying open-file descriptions, so offsets can be shared.

08 · fork_memory.c · C
#include <stdio.h>
#include <sys/types.h>
#include <sys/wait.h>
#include <unistd.h>

int counter = 10;

int main(void) {
    pid_t pid = fork();
    if (pid == -1) { perror("fork"); return 1; }
    if (pid == 0) {
        counter += 5;
        printf("Child counter  = %d\n", counter);
        return 0;
    }
    if (waitpid(pid, NULL, 0) == -1) { perror("waitpid"); return 1; }
    printf("Parent counter = %d\n", counter);
    return 0;
}
▶ Example terminal output
Child counter  = 15
Parent counter = 10
Common beginner mistake: Writing fork(); fork(); starts 4 processes if both forks succeed—not 2. In general, n unconditional successful forks can produce 2ⁿ processes, including the original.

A precise mental model of fork()

Before fork()1 process, 1 instruction stream
fork() creates childchild gets new PID and address space
Two returnsparent: child PID; child: 0
Independent executionscheduler determines order

Linux normally uses copy-on-write: initially the parent and child can share physical memory pages marked read-only. When either writes, the kernel can create a private copy of the affected page. However, the open file descriptions referenced by inherited file descriptors remain shared, including their file offsets. The child inherits environment values and its own logical copy of most process state; it does not inherit the parent's other threads.

Important: Flush or avoid buffered stdio output before fork() to prevent duplicated buffered text. In multithreaded programs, the child should call only async-signal-safe functions until exec(); posix_spawn() can be simpler for launching programs.

int main(void) {
    pid_t pid = fork();
    if (pid == -1) { perror("fork"); return 1; }
    if (pid == 0) {
        printf("Child is doing work\n");
        _exit(7);
    }
    int status;
    if (waitpid(pid, &status, 0) == -1) {
        perror("waitpid"); return 1;
    }
    if (WIFEXITED(status))
        printf("Child exited with status %d\n", WEXITSTATUS(status));
    else if (WIFSIGNALED(status))
        printf("Child killed by signal %d\n", WTERMSIG(status));
    return 0;
}

Buffered-output correction: Before _exit(7), add fflush(stdout);, or print using write(). Alternatively use exit(7) for this simple single-threaded demonstration.

Zombie process

A child has terminated, but its parent has not yet collected its status. Typically displayed as Z or <defunct> in ps.

Orphan process

A living child whose parent has exited; it is reparented to an appropriate reaper such as a subreaper or PID 1, depending on the environment.

Zombie vs orphan: do not confuse them

CaseMeaningWhat to observe
Zombie childChild has exited but its parent has not collected status; its PID and minimal kernel bookkeeping remain.ps -o pid,ppid,stat,cmd may show Z; the parent should call waitpid().

11 · fork_exec.c · C
#include <stdio.h>
#include <stdlib.h>
#include <sys/types.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void) {
    pid_t pid = fork();
    if (pid == -1) { perror("fork"); return 1; }
    if (pid == 0) {
        char *args[] = {"ls", "-l", NULL};
        execvp("ls", args);
        perror("execvp"); // runs ONLY if execvp fails
        _exit(127);
    }
    int status;
    if (waitpid(pid, &status, 0) == -1) {
        perror("waitpid"); return 1;
    }
    if (WIFEXITED(status))
        printf("ls exit status: %d\n", WEXITSTATUS(status));
    return 0;
}

Debugging workflow: example — CPU stuck at 100%

1. Prove the symptomRun top; note the highest CPU process and its PID.
2. Check the process and threadsUse ps -o pid,ppid,stat,etime,%cpu,%mem,cmd -p PID and top -H -p PID.
3. Decide whether CPU or I/O is responsibleHigh CPU + R state suggests active work; long D state and I/O latency suggest blocked storage.
4. Inspect evidenceLook at app logs, /proc/PID/status, /proc/PID/fd; use strace -p PID only when appropriate.
5. Apply a reversible fixConfirm with the owner, tune the workload or correct code, then measure again.

7. Process health / watchdog

Check whether a process is alive and report its CPU and RSS.

● ● ●   process_watchdog.py · PYTHON
import sys
import psutil

if len(sys.argv) != 2:
    raise SystemExit("Usage: python process_watchdog.py PID")
pid = int(sys.argv[1])
try:
    proc = psutil.Process(pid)
    with proc.oneshot():
        print(f"PID: {pid}; name: {proc.name()}; status: {proc.status()}")
        print(f"RSS: {proc.memory_info().rss/1024**2:.1f} MiB")
        print(f"Threads: {proc.num_threads()}")
except psutil.NoSuchProcess:
    print(f"Process {pid} does not exist")
except psutil.AccessDenied:
    print(f"Insufficient permission to inspect PID {pid}")

8. Write historical metrics to CSV

Record 10 periodic CPU/RAM samples and examine trends in a spreadsheet.

● ● ●   metrics_logger.py · PYTHON
import csv
import time
from datetime import datetime
import psutil

with open("usage.csv", "w", newline="") as f:
    writer = csv.writer(f)
    writer.writerow(["time", "cpu_pct", "ram_pct"])
    for _ in range(10):
        cpu = psutil.cpu_percent(interval=1)
        ram = psutil.virtual_memory().percent
        stamp = datetime.now().astimezone().isoformat(timespec="seconds")
        writer.writerow([stamp, cpu, ram])
        f.flush()
        print(f"{stamp}  CPU={cpu:5.1f}%  RAM={ram:5.1f}%")

Discussion / interview questions

Why is fork() efficient for large processes?

Copy-on-write means many virtual pages can initially map the same physical frames; a private copy is created only when a process writes to a shared COW page. Kernel metadata and page tables still have costs.

Why does a shell typically fork then exec?

The shell stays alive as the parent; the child is replaced by the requested executable, while the shell waits or manages the background job.

Can parent and child affect each other’s file offset?

Yes, inherited file descriptors refer to the same open-file description and usually share one file offset. They do not share ordinary writable global variables.

What happens if execvp fails?

It returns -1 in the child and sets errno; the caller must report/handle the error, often ending the child with _exit(127).

What is the difference between a process and a thread?

A process is a resource/address-space container; threads within a process share its address space and many resources, while each thread has its own execution context and stack. Linux models both as schedulable tasks.
